## 2. Короткі відповіді на 7 контрольних питань

### 1) `*aaS` — порівняйте хмарні моделі. Коли яку використовувати?
- **IaaS (Infrastructure as a Service)** — наприклад, AWS EC2, VPC. Провайдер дає «залізо», мережу й диски, а ОС, рантайм, оновлення та застосунок підтримуємо ми. **Коли:** потрібен повний контроль над ОС, мережею або нестандартне системне ПЗ.
- **PaaS (Platform as a Service)** — наприклад, AWS Elastic Beanstalk, Heroku, RDS. Ми деплоїмо лише код/схему даних, а ОС, патчі, масштабування й балансування бере на себе платформа. **Коли:** швидкий вихід у прод для типових веб-застосунків та БД без витрат часу на адміністрування серверів.
- **SaaS (Software as a Service)** — готовий продукт для кінцевого користувача (Gmail, Notion, Figma, Datadog). **Коли:** потрібна готова функціональність «під ключ» без власної розробки.
- **FaaS (Function as a Service / Serverless)** — наприклад, AWS Lambda. Запускаються окремі функції у відповідь на події, оплата лише за реальний час виконання (мілісекунди). **Коли:** вебхуки, обробка подій, рідкісні або дуже спалахоподібні навантаження.

### 2) Регіони, зони доступності (AZ) — що це і навіщо?
- **Регіон (Region)** — географічна область (наприклад, `eu-north-1` у Стокгольмі), де розташовані дата-центри AWS. Обирається за близькістю до користувачів (нижчий ping/latency), законами про зберігання даних (GDPR) і ціною сервісів.
- **Зона доступності (Availability Zone, AZ)** — один або кілька фізично ізольованих дата-центрів усередині одного регіону (з окремим живленням, охолодженням та мережею, але зʼєднаних швидкими низьколатентними каналами). **Навіщо:** для відмовостійкості — якщо впаде один дата-центр (`eu-north-1a`), репліка в `eu-north-1b` продовжить працювати.

### 3) Що таке IaC і в чому його цінність?
**IaC (Infrastructure as Code)** — опис хмарної інфраструктури у вигляді декларативних текстових файлів (Terraform, OpenTofu, CloudFormation) замість ручного клікання в консолі.
- **Цінність:** відтворюваність (однакове середовище для dev/stage/prod), версіонування в Git (історія змін, code review), автоматизація (`terraform plan` показує зміни наперед, `terraform destroy` прибирає все без «забутих» ресурсів) і відсутність людських помилок (configuration drift).

### 4) Різниця між ролями (Roles) та групами користувачів (User Groups) при призначенні політик?
- **User Group** — це постійна сукупність IAM-користувачів, яким видаються спільні постійні права (наприклад, група `Developers` або `ReadOnlyUsers`). Кожен користувач має свої облікові дані, але політики керуються централізовано через групу.
- **IAM Role** — це тимчасова «ідентичність» із набором прав, у якої немає постійного пароля чи ключа. Її можна **тимчасово прийняти** (`sts:AssumeRole`) користувачем, іншим AWS-акаунтом або **AWS-сервісом** (наприклад, EC2 чи Lambda), отримавши короткоживучі тимчасові токени. Це безпечніше, бо права діють обмежений час і не потребують статичних секретів.

### 5) VPC. CIDR, розрахунок блоків адрес.
- **VPC (Virtual Private Cloud)** — логічно ізольована віртуальна мережа у вашому AWS-акаунті.
- **CIDR (Classless Inter-Domain Routing)** — запис діапазону IP-адрес у вигляді `IP/префікс`, де префікс показує кількість зафіксованих бітів мережі. Загальна кількість адрес = $2^{32 - \text{префікс}}$.
- **На нашому прикладі:**
  - VPC `10.0.0.0/16`: $2^{32 - 16} = 2^{16} = 65\,536$ адрес (`10.0.0.0` – `10.0.255.255`).
  - Підмережа `10.0.1.0/24`: $2^{32 - 24} = 2^8 = 256$ адрес (`10.0.1.0` – `10.0.1.255`).
  - **Важливий нюанс AWS:** у кожній підмережі AWS резервує **5 IP-адрес** (перші 4: адреса мережі `.0`, VPC router `.1`, DNS `.2`, майбутні потреби `.3`, та остання `.255` broadcast). Тож у `/24` для наших ресурсів доступно **251** IP-адреса.

### 6) Як влаштовані публічна та приватна підмережі? Що куди маршрутизується?
Обидві підмережі є частиною VPC, різниця — виключно у **таблиці маршрутизації (Route Table)**:
- **Публічна підмережа (`10.0.1.0/24`):** має маршрут за замовчуванням `0.0.0.0/0 -> Internet Gateway (IGW)` і зазвичай автовидачу публічних IP. Ресурси всередині (наприклад, вузол-координатор або Load Balancer) можуть спілкуватися з інтернетом напряму.
- **Приватна підмережа (`10.0.2.0/24`):** у нашій таблиці маршрутизації є лише локальний маршрут `10.0.0.0/16 -> local`. Прямого маршруту до IGW немає, тому з інтернету туди неможливо підключитися напряму — там безпечно розміщують бази даних або шарди KV-сховища. *(Якщо приватним ресурсам потрібен вихідний доступ лише назовні, наприклад для оновлень, додають NAT Gateway у публічній підмережі, але в навчальному кластері ми його не ставили, щоб не платити ~\$35/міс).*

### 7) Коли використовувати `Allow`-, а коли `Deny`-політики?
В AWS за замовчуванням усе заборонено (**implicit deny**):
- **`Allow`** — використовують для стандартної видачі мінімально необхідних прав (принцип найменших привілеїв, як наша `kpi-kv-store-readonly-policy`).
- **`Deny` (explicit deny)** — у правилах оцінки AWS **завжди перекриває будь-який `Allow`**. Його використовують як жорсткий запобіжник (guardrail), коли треба гарантовано заборонити критичну дію незалежно від інших виданих прав — наприклад, заборонити видалення логів, заборонити роботу без MFA або заборонити запуск ресурсів поза `eu-north-1` через SCP в AWS Organizations.
