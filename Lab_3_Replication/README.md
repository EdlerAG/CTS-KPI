Перевірити стан усіх 6 реплік і їхній `offset`:
```powershell
curl.exe http://localhost:8000/shards
```

### 2. Демонстрація запису, читань із різних реплік і падіння вузла
```powershell
# Створити таблицю й записати дані (W=2, R=2 за замовчуванням)
Invoke-RestMethod -Method Post http://localhost:8000/tables -ContentType "application/json" -Body '{"name":"users","partition_key":"user_id"}'
Invoke-RestMethod -Method Post "http://localhost:8000/tables/users/records?w=2" -ContentType "application/json" -Body '{"partition_key":"alice","value":{"role":"admin"}}'

# Декілька читань з r=1: у полі queried_replicas по черзі з'являються leader, follower-1, follower-2
1..4 | ForEach-Object { Invoke-RestMethod "http://localhost:8000/tables/users/records/alice?r=1" }

# Зупиняємо одного фолловера — читання з r=2 і записи з w=2 продовжують працювати!
docker compose stop shard-1-follower-1 shard-2-follower-1
Invoke-RestMethod "http://localhost:8000/tables/users/records/alice?r=2"

# Повертаємо фолловерів — вони досинхронізовуються лише з останнього offset
docker compose start shard-1-follower-1 shard-2-follower-1
```

### 3. Навантажувальний тест (до і після кворумної реплікації)
```powershell

```

## Відповіді на контрольні питання до захисту
1. **Переваги та недоліки реплікації:**
   - *Переваги:* відмовостійкість (падіння 1–2 вузлів не вбиває дані), масштабування читання (балансування на фолловерів), менша затримка при географічній близькості реплік.
   - *Недоліки:* зростання витрат (у $N$ разів більше серверів і дисків), складність синхронізації, можливий лаг реплікації та ризик читання застарілих даних (stale reads).
2. **Математика кворумів $R + W > N$:** якщо запис підтвердили $W$ вузлів із $N$, а при читанні опитується $R$ вузлів, то за принципом Діріхле множини розміром $W$ і $R$ обовʼязково перетинаються щонайменше в $(W + R - N) \ge 1$ вузлі. Опитуючи $R$ вузлів і беручи значення з максимальною версією (`offset`), ми гарантовано отримуємо найсвіжіший запис. (У нас $N=3, W=2, R=2 \Rightarrow 2+2=4 > 3$).
3. **Реплікація з лідером vs без лідера:**
   - *З лідером (single-leader):* усі записи йдуть через одного лідера — простіший порядок подій (лінійна історія), але лідер — вузьке місце запису і при його падінні потрібен failover.
   - *Без лідера (leaderless, як Dynamo/Cassandra):* клієнт пише на $W$ довільних реплік, читає з $R$ і звіряє версії — висока доступність запису без SPOF, але зʼявляються конфлікти конкурентних записів (потрібні LWW або vector clocks і read-repair / anti-entropy).
4. **Навіщо append-only лог подій:** дає незмінну впорядковану історію змін (WAL / commit log). Запис у кінець файлу — це швидкий послідовний I/O (без перезапису B-Tree на місці), гарантує однаковий порядок застосування змін на всіх фолловерах і дозволяє легко доганяти кластер за `offset` після збоїв.
5. **Синхронне vs асинхронне підтвердження:**
   - *Синхронне ($W \ge 2$):* вища надійність (дані точно вже на $\ge 2$ дисках до відповіді клієнту), але вища затримка запису (чекаємо найповільнішого з потрібних фолловерів) і менша доступність, якщо фолловери впали.
   - *Асинхронне ($W = 1$):* мінімальна затримка (відповідь одразу після запису лідером), але якщо лідер впаде до того, як фолловери прочитали лог, останні підтверджені записи можуть тимчасово зникнути.
6. **Через які збої дані можуть тимчасово розійтися:** затримка мережі / лаг реплікації (*replication lag*), розділення мережі (*network partition*), падіння лідера до синхронізації фолловерів, або *split-brain* (коли через збій мережі зʼявляються два лідери одночасно).
